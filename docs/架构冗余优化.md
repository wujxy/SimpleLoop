可以。我们现在这版其实已经收得很干净了。核心不是再给 Proposer 增加“科学方法论设施”，而是**把基础设施边界理顺，然后尽量把研究判断还给 Agent 自己。**

我会把最终的简化/优化方案总结成下面这样。

## 一、总原则

SimpleLoop 不再试图自己规定 Scientist 应该怎么思考。

整体原则变成：

> **Harness 负责构造真实世界、执行真实副作用、保存真实历史；Agent 负责理解这些事实意味着什么，并决定下一步研究什么。**

换句话说：

```text
Mechanism → Harness
Meaning   → Agent
```

Harness 可以工程上很强，但科研判断上要尽量“笨”。

---

# 二、四个基础设施概念

## 1. Workspace：一次 Proposer episode 的临时研究世界

保留当前 `workspace-v0.2.0` 的核心思路，不需要重新拆成一堆 `SourceWorkspace / LabWorkspace / RoleWorkspace`。

每轮：

```text
parent_sha
    ↓
Harness 创建 disposable workspace
    ↓
把任务相关内容挂进去
    ↓
挂载时确定 RO / RW
    ↓
Proposer 在其中研究、修改、编译、probe
    ↓
episode 结束
    ↓
整个 workspace 销毁
    ↓
下一轮重新基于最新 parent_sha 创建
```

所以 Workspace 本质是：

> **这个 agent 这一轮生活在哪个世界里。**

它可以是 writable 的，因为修改只是研究过程中的临时 lab 状态，不会自动成为正式 candidate。

正式 artifact 是否产生、是否 commit，仍由 Harness 控制。

这部分目前方向基本正确，**不用为了“更漂亮的抽象”继续拆。**

---

## 2. Role：职责 + 信息接口，而不是额外权限系统

不需要再造一层复杂：

```text
RolePermission
RoleCapability
RoleView
```

因为 filesystem 权限已经由 Workspace mount 时决定。

Role 只需要表达：

```text
你是谁
你负责什么
你有哪些工具
你能收到什么信息
你交付什么
```

目前保留两个 Proposer 内部角色：

### Generator

负责：

> 基于当前 artifact 独立研究问题，产生新的 hypothesis。

看到：

```text
task / goal
current workspace
source / prior
research tools
```

不获得 History 接口。

### Cognitive / Reviewer

负责：

> 用已有实验历史审查 Generator 的 hypotheses，并判断哪些事实需要反馈。

看到：

```text
same workspace
Generator hypotheses
简短历史上下文
HistoryQuery interface
```

Generator 和 Cognitive **共享同一个 Workspace 没问题**。

它们的信息差异不靠不同 filesystem world，而靠：

```text
Generator → 无 HistoryQuery
Cognitive → 有 HistoryQuery
```

即可。

---

# 三、History 从 Workspace 中独立出来

这是这次比较关键的优化。

以前：

```text
/history.jsonl
/rounds
/repo
```

直接挂到 research environment 里。

虽然本意是给 Cognitive 用，但 Generator 理论上也可以看到。

短期这不是灾难，但长期更干净的设计应该是：

> **History 不再是 Workspace 中的一堆文件，而是一个显式的信息服务。**

即：

```text
Memory / History Service
        │
        ├── search_experiments
        ├── inspect_experiment
        ├── inspect_episode
        ├── search_findings
        ├── inspect_finding
        └── inspect_diff / artifact history
```

只有 Cognitive 获得这个接口。

Generator没有。

这样所谓：

> history-blind generation

才是一个真实的信息边界，而不是：

> “历史文件其实在那，只是 prompt 没告诉模型”。

---

# 四、历史不是“大段注入”，而是“索引 + 按需查询”

这一点我觉得可以定下来。

Cognitive启动时不需要：

```text
把几十轮完整 history 塞进去
```

只给一个轻量入口，比如：

```text
最近实验摘要
相关 Finding 索引
必要的 run-level factual summary
```

然后 Cognitive 自己判断：

> 这些信息够不够？

如果不够：

```text
search_experiments(...)
    ↓
inspect_episode(...)
    ↓
inspect_diff(...)
    ↓
必要时继续查
```

这和成熟 coding agent 对 repo 的使用模式一致：

> **不是先把所有信息塞进 context，而是提供可探索的信息空间。**

History 应该像：

> research archive / library

而不是：

> giant prompt。

---

# 五、Memory 重新定位：资料馆，不是导师

Memory 可以保留两类核心东西。

### Experiment Ledger

这是权威事实：

```text
proposal
parent SHA
candidate SHA
gate result
metrics
status
diff/changed files
```

这个继续作为 immutable factual authority。

### Finding Archive

可以保留，但重新定位成：

> **历史实验的语义组织和检索索引。**

比如：

```text
question
mechanism
code region
experiment refs
```

可以帮助 Cognitive 搜索大量过去实验。

但不要让 Finding 再成为：

> Harness 控制 Scientist 下一步研究的状态机。

也就是说：

```text
Memory stores/retrieves facts
```

而不是：

```text
Memory interprets facts
→ 决定方向是否 exhausted
→ 要求 reframe
```

---

# 六、`explore/` 从在线主流程撤掉

这一点我们已经基本一致。

旧的 `/explore`：

```text
连续失败多少次
family 有没有 improvement
是否 overexploited
是否 challenge_required
```

本质是在 Harness 层试图判断：

> Scientist 是否陷入局部探索。

这在旧 Proposer 比较弱的时候有现实意义。

但现在新的目标是：

> 让一个认知连续的强 Agent 自己看到 evidence 后产生“等等，可能问题不在这里”。

因此：

```text
Explore health
→ 不再作为在线控制信号
```

可以保留一小部分作为**offline telemetry**：

> 方便我们人类分析某个 run 是否高度集中。

但不要再：

```text
Harness:
你已经 overexploited
→ challenge now
```

---

# 七、Harness 变“科研上笨”，但工程上更强

Harness继续拥有：

```text
Workspace lifecycle
RO/RW mount
container/runtime
agent process/session lifecycle
timeout/retry
HEPJob
Git
commit
gate
benchmark
objective evaluation
Experiment Ledger
History service
```

这些都是它应该越做越强的地方。

但从 Harness 中逐渐清掉：

```text
什么时候 reframe
什么时候 challenge
哪个 family 研究够了
必须调用哪个生成元
必须调查几步
必须满足哪个 cognition phase
```

即：

> **Harness 管流程，不管思维。**

这是整个架构简化最重要的一条。

---

# 八、Generator + Cognitive 保持两个角色

这一点现在不需要再纠结合并。

它们拆开不是为了代码方便，而是因为它们拥有不同 epistemic position：

```text
Generator
=
基于当前 artifact 的独立搜索

Cognitive
=
用过去 empirical evidence 对新 hypotheses 做审查
```

所以两个独立角色是合理的。

未来即使换成 Claude Agent SDK：

```text
Generator = Claude Session A
Cognitive = Claude Session B
```

也完全自然。

甚至会更漂亮：

```text
Generator Session A
    ↓
hypotheses
    ↓
Cognitive Session B
    ↓
history audit
    ↓
factual feedback
    ↓
resume Generator Session A
```

这样：

- Generator 的认知连续性一直保留；
- Cognitive 独立访问历史；
- 历史不会污染最初生成；
- 最终如何修改 hypothesis，仍然由 Generator 自己判断。

---

# 九、Agent Runtime 变成可替换底座

基础设施理顺以后：

```text
SimpleLoop 自研 ReAct
Claude Agent SDK
Codex runtime
```

都只是同一层的不同实现。

上层只需要：

```text
launch Generator
launch Cognitive
provide Workspace
provide tools
resume session
receive proposal
```

SimpleLoop 不应该再强绑定某个 runtime。

所以长期可以抽象成：

```text
ResearchRuntime
├── LegacySimpleLoopRuntime
├── ClaudeAgentRuntime
└── CodexRuntime
```

这个抽象值得做，但**不是现在为了架构好看就大改全部代码**。

先把 Workspace / History / Harness ownership 清干净，再换 runtime 会非常顺。

# 十、最终简化后的主架构

我觉得目前可以收成这一张：

```text
                         HARNESS
                            │
               create workspace @ parent_sha
                            │
                  task files + RO/RW mounts
                            │
                            ▼
                 ┌──────────────────┐
                 │ Proposer Workspace│
                 │   disposable      │
                 └────────┬─────────┘
                          │
             ┌────────────┴────────────┐
             │                         │
             ▼                         ▼
       Generator Session        Cognitive Session
             │                         │
       current artifact           current artifact
       research tools             hypotheses
       NO history                 history summary
             │                    HistoryQuery
             │                         │
             └──── hypotheses ─────────┘
                                       │
                                historical audit
                                       │
                                factual feedback
                                       │
                         ┌─────────────┘
                         ▼
                 resume Generator
                         │
                         ▼
                    proposals
                         │
                         ▼
                      Executor
                         │
                         ▼
                       Gate
                         │
                         ▼
                Experiment Ledger
                         │
                  workspace destroyed
```

然后 Memory 独立在旁边：

```text
          Memory / History Service

Experiment Ledger        Finding Index
(authoritative)          (semantic index)
       │                       │
       └──────── HistoryQuery ─┘
                    │
               Cognitive only
```

# 十一、对应当前代码，最值得做的简化

真正需要动的其实没有我们之前想得那么多：

1. **保留当前 Workspace/worktree 设计**，不要重新拆复杂层级。
2. **撤掉 `/explore` 在线控制链路**，最多留下 offline diagnostics。
3. **把历史从 proposer workspace 的公共 filesystem 中逐渐拔出去**。
4. **提供一个简单、明确的 HistoryQuery interface 给 Cognitive**。
5. Generator 不获得 HistoryQuery。
6. 保留 Generator + Cognitive 两角色。
7. `MemoryService` 收缩为“存储 + 搜索”，减少 research-policy 职责。
8. Harness去掉 challenge/reframe/exploration-health 之类认知干预。
9. Agent runtime后续改成 pluggable；Claude Agent SDK值得 A/B，但不需要现在绑定。

所以我现在会把这次重构叫做：

> **不是重新设计 Proposer，而是把 Proposer 周围多余的认知控制设施拆掉，把 Workspace、History 和 Harness 恢复成纯基础设施。**

我觉得这是目前最稳的一步。
